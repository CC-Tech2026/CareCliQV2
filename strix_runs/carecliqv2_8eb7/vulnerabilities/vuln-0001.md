# Production Supabase Service Role Credentials Exposed in Version Control

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-08-25 06:09:23 UTC
**Target:** /workspace/CareCliQV2
**Endpoint:** .env.example
**CWE:** CWE-798
**CVSS:** 10.0
**Fix Effort:** Trivial

## Description

Active production Supabase `service_role` credentials are committed to the repository in both `.env` and `.env.example` files. The exposed service role key provides unrestricted administrative access to the production database, completely bypassing Row-Level Security (RLS) policies that enforce multi-tenant isolation. Validation confirmed the credentials are active and the database contains production data including 25+ users, multiple organizations, and 45+ shifts.

## Impact

Complete compromise of the CareCliQV2 production database and all Protected Health Information (PHI). An attacker with these credentials can:

- Read, modify, or delete **all data** across **all organizations** (multi-tenant isolation bypassed)
- Access **all patient medical records**, session notes, medications, and incident reports
- Exfiltrate **NDIS financial data**, billing records, invoices, and budgets  
- Modify **audit logs** and **compliance records** to hide malicious activity
- Create administrative accounts or escalate privileges
- Delete the entire database or hold it for ransom
- Inject malicious data into patient care workflows

The service role key bypasses all Row-Level Security policies, authentication checks, and application-layer authorization controls. This represents a complete security perimeter breach for a healthcare platform handling Australian Protected Health Information subject to Privacy Act 1988 and NDIS compliance requirements.

## Technical Analysis

Supabase uses JWT-based authentication with two primary key types:

1. **`anon` key** - Public key for client-side use, subject to Row-Level Security  
2. **`service_role` key** - Administrative key that bypasses ALL security policies

The repository contains both keys committed to `.env` and `.env.example`:

```bash
# .env.example (lines 1-4)
SUPABASE_URL=https://sndwllbtmguzduuazahd.supabase.co
SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

JWT decode reveals:
- **Role**: `service_role` (full admin access)
- **Project**: `sndwllbtmguzduuazahd` 
- **Issued**: January 2026
- **Expires**: April 2036 (10-year validity)

The service role key grants PostgreSQL-level `service_role` privileges, documented by Supabase as:

> "The service role key bypasses Row Level Security. Never use it on the client side."

Source: https://supabase.com/docs/guides/api#api-keys

Validation confirmed production status by enumerating tables via PostgREST API:
- `organizations` table: 2 records  
- `users` table: 25 records
- `shifts` table: 46 records

The same credentials exist in both `.env` (active development) and `.env.example` (version controlled template), indicating production keys are used as default values rather than placeholder examples.

## Remediation

**Immediate (within 1 hour):**

1. **Rotate Supabase service role key** via Supabase Dashboard → Settings → API → Reset service_role secret
2. **Rotate Supabase anon key** to prevent unauthorized read access
3. **Update `.env` file** with new credentials on all deployment environments
4. **Audit Supabase logs** (Dashboard → Logs) for unauthorized API access using the exposed key
5. **Notify security/compliance team** for potential PHI breach investigation

**Short-term (within 24 hours):**

6. **Purge credentials from git history**:
   ```bash
   git filter-branch --force --index-filter \
     "git rm --cached --ignore-unmatch .env.example" \
     --prune-empty --tag-name-filter cat -- --all
   ```
7. **Replace `.env.example` with placeholder values**:
   ```
   SUPABASE_URL=https://your-project.supabase.co
   SUPABASE_ANON_KEY=your-anon-key-here
   SUPABASE_SERVICE_ROLE_KEY=your-service-role-key-here
   ```
8. **Force push cleaned history** and notify all contributors to re-clone
9. **Scan for public exposure** using GitHub secret scanning, GitGuardian, or TruffleHog

**Long-term (within 1 week):**

10. **Implement secrets management** (HashiCorp Vault, AWS Secrets Manager, or Doppler)
11. **Add pre-commit hooks** with `gitleaks` or `trufflehog` to block credential commits
12. **Enforce `.env` in `.gitignore`** with CI validation
13. **Restrict service role key usage** to backend servers only (never in frontend/mobile)
14. **Implement Supabase RLS policies** for defense-in-depth (already present but bypassed by service role)
15. **Security training** on credential handling and the distinction between development/production secrets

## Assumptions

Assumes attacker discovers credentials via public repository access, insider threat, or exposed git history. The exposed service role key requires no additional exploitation chain—direct API access grants immediate full database control. Production status confirmed by validation showing real data in user/organization/shift tables.
