# Session Tracking Bypass - Tokens Without JTI Bypass Revocation

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-08-25 06:17:54 UTC
**Target:** local_code: /Users/spurtiratkal/CareCliQV2
**Endpoint:** /api/*
**Method:** GET
**CWE:** CWE-613
**CVSS:** 6.5
**Fix Effort:** Low

## Description

The session tracking mechanism in `device_security_service.py` accepts JWT tokens that lack a `jti` (JWT ID) claim as valid, bypassing session revocation controls. This allows tokens to remain valid even after logout, account suspension, or explicit session termination by administrators. Additionally, tokens with unknown JTI values (not present in the `user_sessions` table) are also accepted as valid.

## Evidence

**Source Code Evidence:**

```python
# backend/app/services/device_security_service.py (lines 82-97)
def is_session_active(session_jti: str | None) -> bool:
    if not session_jti:
        return True  # ← Missing JTI = valid
    try:
        result = (
            _admin()
            .table("user_sessions")
            .select("revoked_at")
            .eq("session_jti", session_jti)
            .maybe_single()
            .execute()
        )
        if not result or not result.data:
            return True  # ← Unknown JTI = valid
        return result.data.get("revoked_at") is None
    except Exception:
        return True
```

**Token Analysis:**

```python
# Token with JTI (tracked):
{
  "sub": "user-123",
  "email": "user@test.com",
  "jti": "abc-def-123",  # ← Tracked in user_sessions
  "exp": 1787650000
}

# Token without JTI (untracked):
{
  "sub": "user-123",
  "email": "user@test.com",
  # NO jti claim
  "exp": 1787650000
}
# ↑ Bypasses is_session_active() check entirely
```

**Impact on Session Management:**

- Normal login creates JTI-tracked tokens (good)
- But JTI check has fallback to "accept if missing" (bad)
- This allows two classes of tokens: tracked and untracked
- Untracked tokens cannot be administratively revoked

## Impact

- **Persistent Unauthorized Access**: Tokens without JTI remain valid until expiration (up to 24 hours default, longer if configured), even after user logout
- **Session Revocation Bypass**: Administrators cannot revoke access for compromised accounts if attacker uses JTI-less tokens
- **Account Suspension Ineffective**: Suspended user accounts can continue accessing the system with pre-generated JTI-less tokens
- **Audit Trail Gaps**: Sessions without JTI are not tracked in `user_sessions` table, leaving no audit record
- **Concurrent Session Limits Bypass**: JTI-less tokens don't count toward concurrent session limits

**Exploitation Scenario**: An attacker with a compromised account or ability to forge tokens (via the JWT secret vulnerability) creates tokens without JTI claims. Even if the account is subsequently suspended or all sessions revoked, these tokens remain functional.

## Root Cause

The function `is_session_active()` is called from `get_current_user()` in `backend/app/core/security.py`:

```python
# backend/app/core/security.py (lines 60-64)
if payload.get("jti") and not dss.is_session_active(payload.get("jti")):
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Session has ended. Please sign in again.",
    )
```

The check uses `payload.get("jti")` which returns `None` if the claim is absent. The subsequent call to `is_session_active(None)` immediately returns `True`, accepting the token as valid.

## Design Flaw

The implementation appears to treat JTI as optional for backward compatibility, but this creates a security gap:

1. **JTI-less tokens bypass all session management**
2. **Unknown JTIs are treated as valid** (assumes "not revoked if not in database")
3. **Exception handling defaults to "valid"** rather than failing secure

## Remediation

**IMMEDIATE:**

1. **Enforce JTI Requirement**
   
   Reject tokens that lack a JTI claim at the validation layer.

2. **Fail Secure on Unknown JTI**
   
   If a JTI is present but not found in `user_sessions`, reject the token rather than accepting it.

**SHORT-TERM:**

3. **Add Monitoring**
   
   Log and alert on tokens without JTI claims being used.

4. **Audit Existing Tokens**
   
   Review if any legitimate flows create JTI-less tokens that need migration.

**LONG-TERM:**

5. **Session Database Constraints**
   
   Ensure all issued tokens have corresponding `user_sessions` entries created atomically.

6. **Token Introspection Endpoint**
   
   Provide admin endpoint to inspect active sessions and force revocation.

## Assumptions

- Attacker has ability to create JWT tokens (either via compromised account or the JWT secret vulnerability)
- Application relies on JTI-based session tracking for security controls
- No secondary session validation mechanism exists
